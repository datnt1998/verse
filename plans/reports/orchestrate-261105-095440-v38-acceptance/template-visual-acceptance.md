## Actionable findings and ownership

### F1 — Desktop template hierarchy and content framing diverge (P2, source-backed mismatch)

Across all four desktop Template sections, the app places the section heading and its explanatory paragraph **on one baseline/row**, while canonical stacks the paragraph beneath the heading. The app setting column also starts closer to the navigation rail and spreads controls wider; the preview panel begins lower relative to the page header. This is not explained by different prompt records or missing preview media. In images/cover, the wider/shorter control groups expose later settings sooner and materially change the vertical rhythm.

**Concrete owners:**
- `apps/viderse/web/src/screens/library/TemplateScreen.tsx:253-275,310-312` (`row2`, settings and aside placement/padding).
- `apps/viderse/web/src/screens/library/libraryTokens.stylex.ts:45` (settings/preview grid column allocation).
- `apps/viderse/web/src/screens/library/template/ImagesSection.tsx:214-217` (`secHead` is a baseline flex row).
- `apps/viderse/web/src/screens/library/template/OutputSection.tsx:158-161` (explicit row section header); corresponding section-header owners are `CoverSection.tsx` and `BackdropSection.tsx`.

**Parent action:** reconcile the actual section header stacking and settings/preview framing against the canonical shell before accepting pixel parity. Keep dataset substitutions separate from the shell fix.

### F2 — Output section adds/repositions layout controls and changes density (P2, source-backed mismatch)

`Template.section.output.png` and `MTemplate.screen.output.png` show an always-present, full-width **“Mở trong Biên tập”** control below layout chips. Canonical desktop places its smaller editor action beside the layout heading; canonical mobile has no such row. In mobile, the additional help paragraph and editor row push file actions much further down the screen. Actual channel avatars are monochrome fills rather than the canonical colored outlined circles, and the output size type is smaller. These are actual presentation differences even though channel descriptions also differ.

**Concrete owner:** `apps/viderse/web/src/screens/library/template/OutputSection.tsx:79-118,145-176` (channel rows, layout markup, unconditional editor link, export size styling). `layoutEdit` is rendered at line109 for both desktop and mobile; this is not caused by fixtures.

**Contract evidence and parent action:** independently read `apps/viderse/docs/design/v1/01-ia-flows.md:281`: Editor is desktop-only and mobile links to it must say **“Mở trên máy tính”**. The actual mobile “Mở trong Biên tập” is therefore a source/copy-contract mismatch, not merely a discretionary design difference. Parent is investigating the route and source-aligned correction; this review makes no source edits. Preserve canonical layout/density while applying that contract. Native channel rows say “Mẫu video mặc định”; canonical includes per-channel current/upcoming video counts. That missing count detail is a data/API-context gap, not proof of a typography defect, and should not be filled with mock counts.

**Integration update (parent-reported, not reverified by this reviewer):** parent repaired the mobile Editor anchor by hiding it for the mobile `hideTitle` branch and using desktop-only mobile hint copy; parent reports the responsive boundary regression failed for phone before the change and passed for desktop. Mark the mobile Editor-link portion **repaired-source / pending-native**. All PNG observations in this report remain evidence of the pre-fix `7daef5fc` capture, not the new local source. Desktop placement/density, channel usage-detail gaps, and the other findings remain distinct. No post-fix tests or screenshots were exercised by this reviewer.

### F3 — Successful import rows show archive filenames instead of imported names (P2, source-backed mismatch)

Both import result pairs have the correct broad success/warning hierarchy, but canonical successful rows use imported names such as “Truyện kể đêm” and “Phim tài liệu”; actual rows show full `SYNTHETIC-…ytf-template.zip` filenames. The `SYNTHETIC-` prefix is fixture data, but the **choice of filename for every successful row is source-backed**, not merely an artwork/data replacement. Long filenames reduce scanability and consume the result title line. The failed row appropriately remains an archive/file identity in both sides.

**Concrete owner:** `apps/viderse/web/src/screens/library/TemplateImportDialog.tsx:213-223`, specifically `name={row.file.name}` at line217. Dialog width520 is set at line180. The app dialog has a taller header/body separation and footer divider than canonical; shared presentation owner is `platform/ui/src/Dialog.tsx:34-52,184-211`.

**Parent action:** reconcile successful-row display naming with the real import result contract, preserving failed-file identity; inspect dialog spacing separately. These fixture-generated done/partial captures do not establish that real ZIP imports succeed or partially fail correctly.

### C1 — Mobile OS chrome is a comparison-context mismatch, not an automatic app defect

Every mobile canonical side contains the iOS 9:41/status strip and bottom home indicator; app captures contain neither. App titles start roughly one status-strip height higher. This alone invalidates raw full-frame pixel parity, but it does **not** justify adding fake OS indicators to the app.

**Relevant actual owners:** `platform/ui/src/kit.css:7-22` reads real `env(safe-area-inset-*)`; `apps/viderse/web/src/screens/library/mobile/MTemplateScreen.tsx:222-232` supplies `MobilePage`. The native browser/safe-area framing must be matched by the capture owner or excluded by an explicitly agreed content-viewport comparison. No clipping defect is asserted solely from this offset.

### C2 — Populated canonical screens are being compared to empty/different actual records (P1 acceptance-context gap)

The canonical template has selected “Đêm xanh rêu”, “Hook đỏ Midnight”, two backdrop channels, fixed sources, snow overlay, and a real completed-video preview. Actual native captures select a different prompt inventory, frequently have no backdrop sources or overlays, and have no rendered preview. Desktop/mobile Library similarly use different template/prompt counts and sort order, and native Backdrops is empty. These pairs cannot validate canonical populated-state fidelity. Do not fix the design by fabricating those records or claim the empty branch matches the populated branch.

**Concrete owners for context selection:** `TemplateScreen.tsx:255-268`, `mobile/MTemplateScreen.tsx:72-108`, and the capture mapping in manifest017. The presentational views consume actual detail/list data. Parent must use a matched, explicitly labeled context to settle populated layouts.

## Acceptance conclusion

The requested representative coverage is complete, but **1:1 UIUX acceptance is not supported**. The clearest source-owned discrepancies are desktop template hierarchy/framing, output editor-action placement/density, and import successful-row naming. Numerous other pairs use different data, empty/populated branches, different templates, or additional error states; those are acceptance-context gaps rather than evidence the underlying design is broken. Mobile full-frame comparison additionally needs a consistent OS/safe-area framing contract. Static rendering review provides no motion or native status-transition proof.
